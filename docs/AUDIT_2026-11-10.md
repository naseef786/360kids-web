# Full-stack audit — 10 November 2026

## Result and scope

Audited the existing Express API, Next.js family/provider/admin application and Expo starter. This pass fixes verified code defects and dependency advisories. It is not a production certification or completion of unresolved product features. Payments and WhatsApp transport remain outside this increment, in line with the current development instruction. All automated records are synthetic.

A final booking safeguard requires the reviewed listing version on submission. If its price or terms changed, the server rejects the stale request with 409 before writing a booking; an HTTP regression covers rejection and refreshed acceptance. The snapshot retains the accepted listing version. Route refreshes also ignore callbacks captured by an older workspace.

## Verification

- Backend: 13 passing Node test cases, TypeScript and production compilation. Tests include real HTTP and Socket.IO connections with embedded PostgreSQL, ordered checksummed migrations, browser-role isolation, tenant access, idempotency, allocation, deadline behavior, suspension, reconnect, token revocation and parallel connection admission.
- Web: 10 passing Node test cases, ESLint without warnings, TypeScript and production build. Tests exercise API retry/account isolation, timeouts, proxy responses, redirect safety, workspace selection, deadlines and notification destinations. These are not browser end-to-end tests.
- Dependencies: `npm audit --audit-level=moderate` passes with zero reported vulnerabilities in all three repositories at the time of this audit. Advisory coverage can change; this is not proof that every dependency is defect-free.
- Mobile: TypeScript and a clean Android JavaScript export pass with patched dependencies. GitHub mobile CI passed, including the online SDK dependency check. The same check timed out locally; the offline check reports no mismatch but explicitly has reduced reliability. This is a starter export, not a native app build or device test.
- Runtime: 12 compiled-server/Next.js production HTTP smoke checks passed, including development startup, liveness/readiness, capability flags, private page shells, unknown/invalid routes and security headers. The unconfigured API must keep liveness at 200, readiness at 503, finance disabled and data routes unavailable rather than pretending a database is connected.

## Migration and rollout

Use the matching backend and web branches. Run **all four** migrations on the intended development/staging database before starting the new API; do not edit migrations 001–003. Back up and rehearse upgrades before production. The migration runner detects changed applied checksums and rolls the transaction back. It also rejects an existing application schema without a migration ledger; an operator must review and baseline it instead of silently adopting unknown tables. Private browser-role revocations assume all business SQL goes through the API, as designed; verify the deployed server database role retains its intended privileges.

`/health/live` proves process liveness only. `/health/ready` checks migration checksums and Auth configuration; it does not prove live email delivery, external Auth availability, payment processing or the entire user journey. Package the SQL migration directory with the compiled server. Keep the expiry worker supervised and Socket.IO traffic on a persistent service with the documented proxy/session-affinity configuration.

## Dependency maintenance

`minimatch@>=7.0.0 <11.0.1` resolves to 11.0.5 in web/mobile. Mobile additionally resolves `glob@>=9.0.0 <14.0.2` to 14.0.2. Unaffected legacy majors are left alone. These overrides cross transitive major ranges; Node 24, lint/type/build and clean Metro export were checked. Remove the overrides when upstream packages adopt patched ranges, then repeat the checks. Do not use `npm audit fix --force` to downgrade Expo or bypass SDK compatibility.

## Remaining release blockers and decisions

1. Hosted Supabase access, migration rehearsal, Auth callbacks/email configuration and privileged-user setup have not been verified from this workspace. No client database migration or real-data import was performed in this audit.
2. No interactive browser or device QA was performed. Verify the responsive matrix, keyboard/screen-reader use, recovery links, route/session transitions, request-form resets and all authenticated journeys on staging. No cloud browser was used.
3. Embedded PostgreSQL is not a substitute for hosted multi-connection concurrency, load, proxy, backup/restore or failover testing. Consistent lock order reduces a known deadlock risk; it does not prove every concurrency scenario.
4. Booking lists remain bounded at 200 records per scope, with active requests prioritized and a visible limit notice. Server-side cursor pagination/search and accurate large-dataset reports remain needed before a larger operational rollout. Public catalog filtering/SEO also needs its planned server-side implementation.
5. Confirm unresolved pending-request/offer expiry/escalation rules, partial-child offers/cancellations/rescheduling, payment recipient/verifier/refund responsibilities, activity variants/packages/free sessions, provider subscriptions and granular staff/branch capabilities before activating dependent launch features. Existing assumptions stay labelled; this audit invents no commercial policy.
6. Approved media/content/policies, private uploads, reliable email/outbox delivery, retention/deletion processing, monitoring/alerting, recovery objectives and release ownership still need completion/approval. WhatsApp large imports/consent/transport and payment integration retain their separate dependencies.
7. The Expo repository remains a welcome-screen starter. Navigation, authentication, booking screens, API integration, native builds and store release are not completed by dependency hardening.

The project remains a development implementation awaiting connected staging validation and remaining scoped work. Passing CI and an HTTP 200 page response are not launch approval.
